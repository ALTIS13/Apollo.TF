# TF metadata import drafts

Baseline: `075ae6983c704cd720aafa19d3b5b50f7358ab3a`. This increment makes reviewed imports durable without claiming that the imported metadata is an identified, playable, or downloadable recording.

## Workflow and ownership

- Spotify: Collection → Spotify → Liked, a playlist, or a saved album → Import metadata. TF uses the connected account's existing paged metadata reads. The review lists the entries in received order, keeps repeated appearances, and reports unavailable upstream positions. It rejects collections above the limit, inconsistent totals, malformed pages and empty results; it never silently takes the first 200 entries. Spotify reads are not snapshot-isolated: an edit that does not change the total can go undetected during pagination.
- File: Collection → Apollo → Imports accepts TF `apollo.tf.playlist-export.v1` JSON up to 128 KiB. Review precedes the explicit save in both flows. Drafts can be reopened and deleted. No track match, playback, download, or bulk library write is triggered by saving or opening a draft.
- API: `GET /api/collections/imports`; `GET`, `PUT`, `DELETE /api/collections/imports/{importId}`. The authenticated account owns the draft, and live `tf.collections` policy and the existing CSRF protection apply. Spotify reads separately require `tf.integrations`. The API accepts at most 200 entries and 90 KiB normalized JSON per draft. A matching `PUT` replay returns the original draft; different content with the same ID returns `import_conflict`. A per-account transaction lock enforces a 30-draft limit across writers and keeps deletion consistent with quota accounting.
- Data: migration `0007_playlist_import_drafts.sql` adds an append-only schema change to the TF database. The runtime can select, insert and delete draft rows; it cannot update them. Each draft stores name, informational source category, ordered artist/title/duration and creation time. No provider identity, IDs, tokens, raw input file, media/lyrics URLs, or audio bytes are retained. Drafts remain until deleted; no new automatic retention or Platform account-deletion orchestration is introduced.
- Browser: HTTP `no-store` for imports, including parser/CSRF failures. Preview and query data stay in memory; owner/session changes discard the review and abort eligible reads. Nothing new is stored in localStorage, IndexedDB or a service worker. An already submitted mutation may finish for the original verified account; stale responses cannot update the replacement session. Expected 409 business errors do not revoke local access.
