# Spotify import ranges

The previous Web importer rejected an entire library, playlist or album above 200 Spotify positions. The import dialog now previews and saves one range at a time: up to 200 provider positions and four 50-row requests per preview. Large sources show the position range and total before confirmation. Moving to another range is explicit; a successful save does not trigger another read or write. Small sources retain their ordinary one-draft flow.

The existing API queries are the documented offset/limit operations for [saved tracks](https://developer.spotify.com/documentation/web-api/reference/get-users-saved-tracks), [playlist items](https://developer.spotify.com/documentation/web-api/reference/get-playlists-items), and [album tracks](https://developer.spotify.com/documentation/web-api/reference/get-an-albums-tracks). There is no new OAuth scope, provider route or quota change. Only user-selected metadata reaches a TF draft. The account draft limit and per-draft storage limits remain unchanged.

Source order and repeated occurrences are preserved. Unavailable positions count toward the range; they do not become phantom tracks or appear as the next range. An entirely unavailable range can still be navigated, but cannot be saved. TF rejects inconsistent totals across the requested pages or between range selections and asks the listener to restart the preview. Offset pagination cannot establish a transactionally consistent Spotify snapshot when tracks reorder or change without a count change. The preview is the exact metadata TF proposes to save, not a promise of a full account backup.

No audio, artwork URL, provider token, or Spotify download permission enters the draft. Matching, verified full-recording selection, playback and independent download permission still use the existing [reviewed recording flow](2026-11-12-tf-reviewed-audio.md).

Chrome fixture: a 202-position saved library showed positions 1-200, then 201-202 on request. Position 201 was unavailable; one explicit confirmation wrote a single draft with only Track 202. The fixture observed no additional writes, audio, or download requests. This was a production Web build against synthetic local API responses, not live Spotify OAuth or persistence on HomeNode. The fixture was stopped after verification.

## Track page follow-up

The liked and playlist track adapter now rejects an empty upstream `items` array before the reported end and rejects arrays larger than the requested `limit`. It still accepts an empty terminal page and pages whose raw positions are present but unavailable (for example, null tracks). For Spotify's documented [album takedown sentinel](https://developer.spotify.com/documentation/web-api/reference/get-users-saved-tracks), a track with a valid Spotify ID and an empty album name counts as unavailable; the adapter preserves neighboring track order and the provider's total. It does not invent a title for the album or expand provider permissions. Saved albums and album tracks use their existing separate reader.

Four regressions failed before the correction. All 58 cases in the affected provider test file then passed, along with the integrations typecheck and build. ## Short provider pages

Spotify's `limit` is a maximum; the provider returns a `next` page reference. A short response can therefore advance by less than TF's requested 50 positions. The adapter now completes the original window for liked, playlist and album tracks using up to four upstream requests under the existing command deadline. It validates that the continuation is for the same Spotify resource, advances past the received raw positions, and stays within the original window. Only the validated offset is used; the adapter reconstructs the original endpoint and remaining limit, and forwards none of the continuation URL's other query parameters. Explicitly skipped positions stay skipped. If there is no continuation, the raw rows must cover all remaining positions in the requested window without exceeding the reported total. A changed total, zero progress, invalid continuation or exhausted fragment budget fails the read rather than saving a partial window.

There are still at most four TF API requests in a 200-position Web preview; the upstream budget is separately bounded per TF page. No browser response, signed command, OAuth scope or storage schema changes. This is not a stable snapshot if Spotify reorders tracks without changing the total. Four fragment regressions and two terminal-page regressions failed before the corresponding fixes. The affected provider and service files pass with typecheck and build. No real Spotify call or repack of the frozen candidate.
