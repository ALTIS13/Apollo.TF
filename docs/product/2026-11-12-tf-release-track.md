## Delivered Spotify slice

`TF_INTEGRATIONS_SPOTIFY_PLAYLIST_API=items` explicitly selects the new upstream path and response keys. Unset or `tracks` preserves the legacy profile for existing registrations. Invalid values fail config parsing. The two ordinary source Compose files and the non-frozen Coolify template pass the setting to `tf-integrations` only. No deployed Compose environment or frozen canary was changed. A `403` never falls back to the other route. Metadata-only followed lists with omitted contents are excluded in `items` mode only after metadata validation; malformed and wrong-profile responses fail. The adapter scans at most five 50-row pages using computed offsets and returns up to 50 readable playlists in existing DTO order; if the scan budget cannot establish an empty library it reports unavailable rather than a false empty result. `total` remains upstream total, not the number scanned or readable. Null, local and non-track playlist rows are not importable. No new API/identity/migration/OAuth scope or media permissions.

Verification: 3 expected failing regressions before implementation. Review reproduced 5 failures (second-page playlist, malformed/wrong profile and two Compose boundaries) and then one zero-progress page regression. An empty page before upstream `total` now fails as unavailable. Final run: 66 affected provider/config/service/runtime/Compose cases pass. Integrations typecheck/build and Web production build pass. Web retains known sourcemap/chunk warnings. [Local preview](http://127.0.0.1:7456/discover) was opened through Chrome: recommendations rendered, play/pause worked with generated fixture WAV, no overlay or relevant console errors. No actual Spotify API request or OAuth, provider audio, release publication or native install was performed.

1. **Web/catalog:** extend approved user-selected metadata intake, including saved albums and paged results; preserve provenance and unmatched rows. Add artist navigation using the existing Discover and library actions rather than another player. Build a licensed/owned sample catalog with known full, clean edit, alternate recording, preview and unknown cases; verify match and download decisions separately.
2. **Web runtime:** use TF-only Coolify/container release tooling and the root-owned exact issuer/JWKS, entitlement, renewal/revoke, fixture, recovery, image/digest and cleanup receipts. Current `1f49e42` source intake is not a running release and does not silently take these changes. Before publishing, prove authenticated end-to-end search, decoded full-length playback, import, save, and an allowed download; ensure unrelated HomeNode/Caddy services remain unchanged.
3. **Android:** existing mobile source uses old client-session and socket authentication; do not ship that against the protected TF API. Agree on Platform native registration, system-browser PKCE/exact redirect, TF session/renewal and ticket ownership. Build a source-bound Gradle APK without relying on Expo Go or EAS delivery; preserve signing continuity. Validate on A063, including system controls, background/resume, revoke and offline restrictions. Toolchain presence is not APK proof.
4. **Windows:** browser launch is the current Quasar bridge, not an installed TF app. Reuse the Web client in a signed desktop host or coordinated Quasar module after the shared auth/launch contract, without a duplicate login/updater or bypass of signing. Verify exact installer, native start/media keys, entitlement/revoke and rollback. Do not wake paused Quasar work based on this plan alone.

Goal stays active across these steps. Work on independent TF source slices while runtime admission remains pending; do not misreport a fixture, unsigned shell or open browser tab as a release.
