# Import from a Spotify account data file

In Web, open Collection > Apollo > Imports and choose the Spotify library file. Select the extracted `YourLibrary.json`, not the whole ZIP or the history files. [Spotify's account-data guide](https://support.spotify.com/us/article/understanding-your-data/) describes the JSON export and its saved-library contents. It does not publish a stable field-level schema. This adapter recognizes the observed `tracks` array and its `artist`, `track`, and music `uri` fields. [LyricLens's parser](https://github.com/udirno/lyric-lens/blob/0807e41fdd6f5eeebe2863f01357cf3e2c743db3/scripts/ingest_spotify.py) and [Spotify Taste Profiler's loader](https://github.com/jasonwaterfalls/spotify-taste-profiler/blob/ac7089ab46a5c55deab401282457f27dd45dd6ae/src/extract.py#L225-L237) were used as format references only. No code, data, account archives or audio was copied from either project.

The browser accepts up to 2 MiB and 10,000 track positions. It retains only artist/title and a marker for each unavailable row in memory. The URI identifies a supported row and is then discarded; duration is unknown, not guessed. Podcast, local-file and malformed track rows are not offered as importable. Other archive sections are ignored. A range contains up to 200 positions and keeps the original order and repetitions. An empty range does not hide subsequent ranges. The existing 90 KiB normalized draft limit and account draft quota still apply; oversized ranges are not silently truncated.

Nothing is written when the file is opened or a range is changed. A confirmed range uses the same account-scoped `source: file` draft with existing `tf.collections` and browser CSRF checks. The archive, provider IDs and other private fields never become part of the request. This does not authorize playback or download and does not replace Spotify OAuth. No server schema, provider permission, platform identity or production configuration changed.

## Verification

22 focused parser/collection cases passed, including original TF-file behavior, preview limits, cancellation, owner change, duplicate tracks and a sanitized explicit save. Music-player typecheck and production build passed; existing Vite warnings remain.

The final Web build ran in Chrome against a stopped-after-use loopback fixture with `tf.collections` and `tf.search`, without `tf.integrations`. A synthetic file opened via the real file chooser. The first 200 positions were unavailable; the next range 201–203 contained two repeated tracks and one skipped local entry. Opening and paging made no writes. Explicit save sent one normalized metadata PUT, accepted as one draft with two entries. The fixture observed no Spotify, audio or unexpected requests, and Chrome reported no warnings or errors. No private account archive, live Spotify OAuth, real TF database, or device install was used in this check.

## Playlist files

The same picker also recognizes extracted `Playlist*.json` files: an object with a `playlists` array, or the observed top-level array variant. A playlist has a name and ordered items; only the music entries with track and artist names and a Spotify track URI are recognized. The observed container and item shape are documented by the [reference loader](https://github.com/jasonwaterfalls/spotify-taste-profiler/blob/ac7089ab46a5c55deab401282457f27dd45dd6ae/src/extract.py#L267-L274) and its [playlist normalization](https://github.com/jasonwaterfalls/spotify-taste-profiler/blob/ac7089ab46a5c55deab401282457f27dd45dd6ae/src/normalize.py#L211-L249). These are schema observations, not an upstream compatibility promise or copied implementation.

Select the intended playlist within the file, then review and save one range. Position and save state are scoped by playlist and range, not by playlist title. The 2 MiB and 10,000-position limits apply to the whole file, with at most 1,000 playlists and the same 200-position/90 KiB draft bounds. Playlist names, artist/title and order are retained as needed; user IDs, dates, links, podcast and local-file payloads are not uploaded. A malformed playlist container is rejected rather than silently dropping part of the file. Saved album exports, history and the whole ZIP are not supported by this path.

27 focused parser and collection cases, typecheck and the Web production build passed. Preview produced no writes; explicit confirmation saved only two matching occurrences in one metadata PUT. The first playlist still offered its own Save action afterward.
