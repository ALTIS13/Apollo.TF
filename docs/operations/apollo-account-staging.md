## Secret custody

Create only the three new root-owned directories above, mode `0700`. The secret directory must contain five regular, non-symlink, single-line files:

| File | Purpose |
| --- | --- |
| `account_postgres_password` | fresh PostgreSQL bootstrap/superuser password |
| `account_auth_db_password` | distinct password for `supabase_auth_admin` |
| `account_legacy_jwt_secret` | fresh legacy HS256 compatibility secret, at least 32 characters |
| `account_jwt_keys` | `JWT_KEYS` JSON array from the pinned Supabase asymmetric-key generator, including the ES256 private key and legacy key |
| `account_publishable_key` | opaque `sb_publishable_...` client key from the same generation run |

The pinned sources are `docker/utils/generate-keys.sh` followed by `docker/utils/add-new-auth-keys.sh` at commit `e1af732589cd468edb49500ebc04e4367d4c56ad`. The first script needs OpenSSL. The second needs Node.js 16 or newer (HomeNode has Node.js 18.19.1) or a running Docker daemon, reads `JWT_SECRET` from `.env`, and emits `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `ANON_KEY_ASYMMETRIC`, `SERVICE_ROLE_KEY_ASYMMETRIC`, `JWT_KEYS`, and `JWT_JWKS`.

Do **not** run those upstream scripts for live Task 1 keys as-is. The pinned `add-new-auth-keys.sh` passes `JWT_SECRET` to its embedded Node program through `argv`, where another same-host process may observe it. Before secret creation, root must separately review a scoped adaptation that keeps the pinned EC P-256/ES256 and opaque-key semantics but supplies the legacy secret over stdin and writes only to a mode-`0600` operator file. Retain only `JWT_SECRET` as `account_legacy_jwt_secret`, `JWT_KEYS` as `account_jwt_keys`, and `SUPABASE_PUBLISHABLE_KEY` as `account_publishable_key`; create the two distinct database passwords independently. Never persist or transfer `SUPABASE_SECRET_KEY`, either generated service-role JWT, `JWT_JWKS`, or database URLs into this Application. No live key-generation command is authorized until that adaptation is reviewed.

Copy only these five retained values over the approved encrypted administrative channel and remove the operator temporary file after both the HomeNode copy and encrypted recovery escrow are verified. Never paste them into Git, Coolify logs, deployment output, chat, or client code.

On HomeNode set every secret file to `root:root` mode `0444` and keep the parent directory `root:root` mode `0700`. This deliberately follows Docker Compose's Linux file-secret behavior: a file source is a bind mount and Compose silently ignores per-service `uid`, `gid`, and `mode`. The root-only parent protects host traversal, while only services explicitly granted a secret can see its read-only mount. Auth runs as uid 1000 and Envoy as uid 101. Reject symlinks, multiline values, missing final values, a publishable key that does not match `^sb_publishable_[A-Za-z0-9_-]{16,128}$`, non-array JWT key JSON, identical database passwords, or any directory/file mode drift.

## Backup, rollback, and recovery

Coolify configuration backups do not back up Application volumes. Before any schema-changing proof, install the reviewed export helper into the root-only operator directory and run it as root:

```sh
install -o root -g root -m 0500 deploy/supabase/account/backup-export.sh \
  /var/lib/apollo-account-staging/operator/backup-export.sh
printf 'Reviewed 40-hex source commit: ' >&2
IFS= read -r source_commit
case "$source_commit" in *[!0-9a-f]*|'') exit 1;; esac
test "${#source_commit}" -eq 40
/var/lib/apollo-account-staging/operator/backup-export.sh \
  --backup-root /var/lib/apollo-account-staging/backups \
  --secret-directory /var/lib/apollo-account-staging/secrets \
  --source-resource apollo-account-staging \
  --source-git-commit "$source_commit"
```

The helper validates the explicit resource name and 40-character lowercase source commit, resolves both roots to absolute non-filesystem-root paths, and requires exactly one running database carrying the matching stack/component/resource/source-commit labels. It also verifies the two mounted volume names match that resource. Zero or multiple matches and label/volume drift fail closed. It streams a custom-format `pg_dump` **with ownership and ACL entries retained**, archives the complete `/etc/postgresql-custom` tree, copies all five continuity secrets, and records the exact resource, source commit, image, server version, two volume names, signing `kid`, and RFC 7638-style public EC JWK thumbprint. It writes and verifies `SHA256SUMS` before atomically publishing the timestamped mode-`0700` bundle. Its secret copies are mode `0400`. The bundle is plaintext and root-only; never copy it off HomeNode until the approved encryption recipient, tool, and transfer procedure are configured and tested.

PostgreSQL 17 ignores `pg_dump --no-owner` for custom archives, but `pg_dump --no-acl` really omits grant/revoke entries. The exporter therefore uses neither flag. `pg_dump` does not include cluster-global roles; recovery depends on first initializing a fresh PG17 volume with the same pinned Supabase image and `roles.sql`, then restoring as `postgres` with neither `pg_restore --no-owner` nor `--no-acl` so archived ownership and privileges are replayed.

The user-approved Windows destination candidate is `C:\Users\maksi\Documents\Apollo.Backups\Apollo.Platform`, but off-node encrypted transport is `NOT_CONFIGURED_PENDING_PROXMOX_DESIGN`. Do not create it, install encryption software, export plaintext, or schedule a job from this runbook. The Proxmox inventory currently has only local/local-lvm storage and no PBS; a Proxmox VM backup/image is therefore not yet an operational backup. Once designed, VM-level backup is an additional recovery layer and does not replace the logical database/config/five-secret bundle.

Target retention is seven successful daily logical bundles on HomeNode and, after encryption is configured, 30 daily plus 12 monthly encrypted off-node copies. Enforcement and deletion are `NOT_CONFIGURED`; no automatic pruning is authorized. ## Platform session-liveness integration gate

The Platform adapter is not allowed to treat Auth `/user` as a strict session-revocation oracle. For sensitive actions it will eventually check the exact authenticated `session_id` plus `sub` against `auth.sessions` through a dedicated backend PostgreSQL role. That role may receive only `CONNECT` on database `postgres`, `USAGE` on schema `auth`, and `SELECT (id, user_id)` on `auth.sessions`; it must be login-capable, non-superuser, non-createdb, non-createrole, non-replication, non-bypassrls, have no memberships, and be unable to select any other session column.

The role/bootstrap and its file-backed checker DSN do not exist in this Task 1 package because `auth.sessions` is created by the pinned GoTrue migrations at runtime. Status is `NOT_CONFIGURED_INTEGRATION_GATE`. After the first authorized migration, Platform/Web must provide the reviewed bootstrap and database-interface contract, and runtime tests must prove both the allowed exact-column lookup and SQLSTATE `42501` for a forbidden column before sensitive-action liveness is enabled. Do not reuse a superuser, `supabase_auth_admin`, publishable key, or service-role assertion for this interface.
