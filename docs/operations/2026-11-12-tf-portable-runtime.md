# TF portable runtime and data lifecycle

Status: rollout design, not a deployment receipt. The first target is a TF-only **Coolify Application**, not an unmanaged Compose stack, a Coolify Service, or a change to the shared HomeNode ingress. Source features are integrated before selecting a new image set. Existing frozen canary inputs, other projects, DNS, Caddy, and firewall rules stay unchanged.

An older source-admitted manifest or a reachable Coolify instance does not satisfy the current image, issuer, audience, entitlement, renewal/revoke, or cleanup receipt.

## Client Cache And Device Data

| Data | Owner and retention |
| --- | --- |
| Fingerprinted app assets | The [Web nginx configuration](../../artifacts/music-player/nginx.conf) revalidates HTML, SPA routes and nonfingerprinted files. Vite fingerprinted assets cache for one year; a missing chunk returns a non-cacheable 404 rather than SPA HTML. The static container rejects same-origin API requests instead of pretending to be the API. A future service worker may cache only an explicit app-shell allowlist. Do not intercept API, media, auth callbacks, or cross-origin provider responses with a generic cache-first rule. |
| Auth, provider metadata, library snapshots | Server authority; private API responses `no-store`. Keep provider data in memory only, keyed by verified TF account, installation, provider subject, and operation/pagination. Cancel requests and invalidate account queries on switch, logout, disconnect, or revocation. A late response cannot resurrect the prior owner's catalog. Never persist provider tokens, OAuth code, CSRF, or account payloads to browser storage. |
| Preferences, recent searches, queue/resume | Web local storage keys use account, installation and schema version for recent searches (up to 8, 30 days) and queue (up to 500, 7 days). Expired records are removed on the next scoped read, not by a background timer while the app is closed. Queue snapshots keep order and position but no provider artwork URLs on new writes, and ignore old URLs on read; a normal write replaces legacy data. Explicit sign-out removes the current account/installation's two local keys even when the server request fails. It does not remove server collections, other keys, or bytes saved outside TF. This is best effort if browser storage is blocked and is not a cross-tab revocation guarantee. Transient connectivity loss preserves resumable state. |
| Android and Windows private state | Only after Platform native session admission, use Android Keystore/Windows DPAPI-backed custody for session material. Keep private data app-local and out of Android cloud/transfer backups and Windows roaming. Scope the database to installation, account and schema; check admission before reading private state. Keep cache size, eviction, and explicit removal separate from authorized downloads. Prove upgrade, sign-out, installation change and disk-full handling on each actual client; Web storage checks do not qualify either native client. |
| Offline audio | Not enabled by this design. Require independently proven per-recording source rights and Platform-issued offline admission with expiry, replay protections and revoke-on-reconnect. Loss of network does not extend a lease; do not claim instantaneous server revocation on a disconnected device. Quotas, LRU/expiry, and removal on sign-out/revoke must be tested before allowing disk persistence. |

The saved-albums query is a session-scoped catalog read, not a downloaded library. A valid link, a full recording, permission to download it, and offline admission are separate conditions.

Native release blocker: the legacy Android library uses unscoped AsyncStorage keys for job/library records and can write both app documents and Media Library copies. Do not carry that behavior into managed offline storage. Treat an explicit export outside app custody as a separate operation; TF cannot promise to revoke a user-owned copy. Existing device files were not changed. The Windows bridge currently opens the Web listener; no TF Windows disk implementation was qualified here.

For both native clients, keep three separate stores and controls: server-synced library data, an evictable local cache, and explicitly admitted offline downloads. Clearing cache must not delete favorites or valid downloads. Set a byte budget for cache and a separate user-visible offline limit before enabling either on disk. Fetch to a bounded temporary file, verify size and digest, then publish atomically; remove incomplete writes on recovery. On reconnect reconcile server revisions before showing private state as current. Account switch, explicit sign-out, installation reset and entitlement expiry/revoke invalidate private state for that scope, including managed offline admission. A cold start with missing/corrupt storage should fall back to fresh online data, not a different account's snapshot. Verify with two accounts, an app upgrade, a low-disk/interrupt scenario, and an expired lease while disconnected. Keep existing user exports out of automatic cleanup.

Web cache proof (2026-11-13): the old Dockerfile's configuration returned SPA HTML for a missing JS asset. With the new config, local [nginx for Windows](https://nginx.org/en/download.html) served a production Vite build on loopback and passed nine checks: HTML/deep-link revalidation, conditional 304, existing hashed and unversioned assets, missing asset, favicon, static-origin API rejection and health. Only listen address and document root were remapped. No OCI build or Coolify/Caddy deployment was performed.

## HomeNode Application And Cleanup

1. Select exact TF source, immutable image digests, protected secret bindings, dedicated TF databases/queue, explicit public hostnames and target destination. Use [Coolify's Git-backed Docker Compose Application](https://coolify.io/docs/applications/builds/docker-compose); keep non-TF bridges and production migrations untouched during validation. Confirm capacity and rollback resources before launch.
2. Verify the TF-only project/destination and resolved compose inputs (without exposing env values); run one disposable acceptance candidate before production. Prove health, login, entitlement and revoked session, full authorized audio, download TTL and scoped cleanup, and a rollback. Promote only the same verified digests under the coordinated runtime packet. A disconnected fixture is not acceptance.
3. Keep existing rotated container logs and worker TTL/byte limits. The worker defaults to a 24-hour file TTL, a 20 GiB owned-storage quota and a five-minute sweep; the API supplies one-day/200-record retention for each BullMQ terminal result class (BullMQ applies it on subsequent finalization, not on a wall-clock schedule). A resolved sweep that cannot verify or satisfy the quota now produces a worker `warning` even if it did not throw. None of this measures other HomeNode data or proves cleanup there. Before sustained traffic, measure TF volume usage and free space on the destination, verify terminal-job retention on an idle queue, and observe sweep and queue health during a disposable soak.
4. Resource retirement is owner-scoped. Remove only exact TF Applications, their stopped release containers and no-longer-required images after verifying rollback retention. Preserve backups and independently inventory volume ownership/mounts first. No global `prune --volumes`, shared-network deletion, automatic deletion on rollback, or server-wide cleanup setting changes. [Coolify cleanup documentation](https://coolify.io/docs/core/infrastructure/servers/automated-docker-cleanup) also distinguishes unused volumes from disposable data.

Record the source revision, image digests, Coolify Application and destination IDs, retained rollback image, and a before/after inventory for each TF rollout. Count scoped image/build growth, log rotation, queue age, expired artifacts and owned volume growth during the soak. Build off HomeNode when a separate build host is admitted; target hosts pull the exact images. A cleanup candidate needs an owner, a retention reason and proof that no running or rollback Application references it. Report unknown objects for review instead of treating them as debris.

## Scale, Move, Retire

- **Single-node default:** retain the existing internal Compose DNS and private networks. The current worker uses a local downloads volume. Its filesystem must not be assumed shared by separate Coolify destinations; copying a container does not move its durable state.
- **Compute split first:** use an independently versioned TF search or integrations Application on another node. Publish no PostgreSQL/Redis/worker ports to the Internet. Bind module/control origins by deployment profile, not hard-coded HomeNode addresses; use authenticated private transport, TLS across hosts, scoped command/heartbeat keys, readiness, version compatibility, and measured latency. A read-only topology verifier should reject insecure external origins, a missing owner, shared/unidentified storage, or inconsistent module revisions before any apply step. The TF integration database remains separate and is migrated by one authorized runner.
- **Load balancing:** use a separate private L7 target pool for stateless modules with health-aware routing, draining, and rollback. Coolify's [multi-server feature](https://coolify.io/docs/core/infrastructure/scaling/multi-server-deployments) does not replicate a Compose Application across destinations; use distinct Applications for split profiles. API horizontal expansion requires tested shared session/ticket state and verified WebSocket reconnect/notification delivery across replicas, not just a proxy stanza. Search caches can be disposable per replica; account-bound suggestions and tenant isolation must remain correct on a miss. Do not change shared Caddy until a TF-only route and rollback have been checked.
- **Downloads:** before adding competing workers on different nodes, replace local-path assumptions with an authenticated artifact locator (prefer private object storage with object-level lifecycle and short-lived admission) or explicit owner routing. Bind artifacts to account, job, digest and expiry. Shared queue, cancellation, visibility of final files and writer fencing need real two-worker proof. For a worker move without that capability, drain, retire expired artifacts, and bring up a single replacement after confirming no active writers.
- **Full move:** capture exact TF resource/image/storage inventory and create a consistent versioned backup; restore into a fresh destination and verify migrations, account isolation and checksums. Drain queue and fence writers, move final state, bring up target read/health checks, then cut traffic. Verify authenticated web, an allowed full track, download lifecycle, entitlement/revoke, and restoration before retiring source. Revert ingress and single-writer ownership together on failure; never operate both authoritative DB writers blindly.
- **Old-node deletion:** retain the rollback window. Prove traffic is off the old node, no mounted or shared resources remain, new restore/acceptance passed, and backup custody is confirmed. Require exact resource IDs and separate authorization for permanent deletion of data. Remove only identified retired TF resources and verify unrelated HomeNode services before and after.

### Move inventory

| State | Handoff |
| --- | --- |
| Search cache, suggestions, tmpfs and rotated logs | Recreate the Application on the target; no cache copy. Preserve diagnostic evidence only if needed. |
| TF Postgres 16 and integrations Postgres 17 | Back up and restore separately. Keep the integration token keyring under separate custody; without it, restored connections may require reconnection. Test restoration and fence the source writers before transfer of authority. |
| API Redis (sessions/cache) and download Redis (queue) | Treat session revocation state and job state as security/consistency data, not disposable cache. Keep the services separate; plan session re-admission with Platform if sessions are not migrated. Drain or reconcile every queued and in-flight download before moving its file store. |
| Reviewed catalog/media binds and download files | Verify reviewed inputs by digest on the target. Keep retained download bytes paired with job ownership and expiry, or explicitly expire them; never treat a host path as a distributed file reference. |
| Images, networks and secret bindings | Pull by digest, attach only dedicated target networks and issue/bind scoped target credentials. Check old references after cutover; retire by exact ID only after rollback expires. |

## Search Compute Application

[The standalone search profile](../../deploy/coolify/apollo-tf.search-compute.git.compose.yml) is a single destination Git Compose Application with one search process. It uses a release image digest, two file-backed keys, read-only root, bounded tmpfs/CPU/memory and rotated logs. It has no persistent volume, database, Redis, or published host port. The base single-node profile still works unchanged. Moving search discards its process-local cache and suggestions; it does not move account data or recordings.

From the repository root, run the static preflight against a separate file of operator declarations (do not pass the real application secrets):

```powershell
pnpm release:validate:tf-search-compute --declarations-file '<operator>/tf-search-compute.env'
```

Use the [example declarations](../../deploy/coolify/search-compute.env.example) as a starting point. Only the image digest, version, deployment time, secret directory and heartbeat origin are passed to the Compose render. The remaining declarations compare the API-side search origin with the declared listener and destination and provide a capacity ceiling; they are not settings that create a listener or reserve capacity. A positive result is not proof of private reachability, certificate trust, capacity, secret readability, or permission to start the Application.

Local proof (2026-11-13): 35 focused cases and scripts typecheck passed. Compose v5.4.0 rendered the tracked profile with synthetic declarations and reported one service, two networks, `compose-config-only`, and `activationAllowed: false`. The root command rejected the example's zero digest. No Docker daemon or live Application was used.

1. Admit the exact source/image, destination, and private HTTPS listener first. The listener must be reachable by the TF API only over the admitted private route and attach only to the dedicated control network on the search destination. A Docker bridge does not connect two hosts. Do not add a public Coolify domain, shared proxy attachment or global Caddy rule. Prove approved DNS/TLS, provider egress, private heartbeat ingress on the TF API and non-reachability from outside the approved route.
2. Stage fresh command and heartbeat keys separately on the destination and bind the matching counterpart at the API (`TF_SEARCH_INTERNAL_AUTH_SECRET_FILE` and the `search-media` entry of `APOLLO_MODULE_HEARTBEAT_KEYS_FILE`). Confirm UID `10001` can read the actual files without showing their values. Set `TF_SEARCH_COMPUTE_IMAGE_DIGEST` (bare 64-hex-digit SHA-256), `TF_SEARCH_VERSION`, `TF_SEARCH_DEPLOYED_AT`, `TF_SEARCH_COMPUTE_SECRET_DIRECTORY`, and `TF_SEARCH_COMPUTE_HEARTBEAT_API_ORIGIN` in the protected application inputs. A successful Compose render does not verify any of those values against the host.
3. Bring the new search process up against a dedicated acceptance API first. Prove readiness, signed requests, replay rejection and heartbeat; measure timeout, provider capacity and cold-cache latency. For cutover, stop routing to the old search, drain it, and switch the API to the exact private HTTPS `TF_SEARCH_ORIGIN` with insecure HTTP disabled and the admitted command/heartbeat key binding. Do not send live requests or accepted heartbeats to/from both destinations with the same key. Roll back the API origin and key binding together; keep the old image and scoped rollback resources until acceptance ends.
4. A future private balancer must keep signed request bytes intact, avoid blind retries, drain old targets and pass a two-instance replay/limit test. This requires atomic shared replay admission or separate target-bound signing, a shared provider budget, and per-instance health. Until then use one active target. Search has no durable storage to migrate; retire only the exact old Application, its dedicated network if unused, and retired keys/images after rollback retention. Full API/worker migration still follows the restore and writer-fencing steps above.

The reviewed Web profile already has its own topology validator. Its TF API currently uses the literal local `http://tf-search:8080` and waits on that service. A Coolify environment variable alone does not override these literals. Before a split cutover, prepare a separate source-bound API-side profile that binds the exact private origin, disables insecure HTTP, and removes the local search dependency and service from that profile. Preserve the existing single-node profile for rollback. A live private listener, balancing and cross-node stateful migration are not included in this search source profile.

### Balancer acceptance

Keep the single-destination path as the default. The first scalable target is an optional private balancer Application and two separately registered search Applications, not a balancer in the shared Caddy configuration. Configure targets by admitted HTTPS origin and destination, with a stable API-facing origin. Add a new target at zero traffic, pass readiness and authenticated command checks, then shift a measured fraction and compare latency, error rate and provider consumption. Drain existing requests before removing a target; an ambiguous timeout must not trigger transparent replay on another target. The balancer must not own a database, media volume, user session, or provider credential.

Before this can receive real traffic, prove atomic nonce admission across destinations, a provider-wide request budget, per-instance heartbeat identity, and tenant isolation after a cache miss or target failure. Include the ability to set one target to zero, run entirely on the replacement, and return to the previous target without changing the public TF URL. Verify the transport and routing in a disposable two-destination rehearsal first. No new public domain is needed for this source stage.
